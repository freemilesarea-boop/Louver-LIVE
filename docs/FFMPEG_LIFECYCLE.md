# FFmpeg 생명주기와 백엔드 배포

247streams 는 유료 고객의 24/7 방송을 송출한다. 백엔드를 배포하면 그 방송이
끊긴다. 이 문서는 **왜 끊기는지**, **어떤 구조가 그것을 바꾸는지**, 그리고
**무엇이 어떤 구조로도 바뀌지 않는지**를 코드와 실측으로 정리한다.

읽기 전용 상태 점검은 `docs/YOUTUBE_OAUTH.md` §8 과 `scripts/youtube-audit.sh`
를 보라. 이 문서는 프로세스 구조에 대한 것이다.

---

## 1. 지금 구조 — 코드가 말하는 사실

| 사실 | 위치 |
| --- | --- |
| FFmpeg 은 `Command::new(program).spawn()` 으로 뜬다. `setsid` 도, 프로세스 그룹 분리도 없다 | `louver-core/src/streaming/supervisor.rs:413-425` |
| stdout 은 `-progress pipe:1`, stderr 도 파이프. **둘 다 서버 프로세스의 스레드가 읽는다** | `supervisor.rs:429-461`, `ffmpeg.rs:568` |
| "worker" 는 서버 프로세스의 OS 스레드이고, `ProcessHandle` 을 들고 있다 | `louver-cloud/src/manager.rs:235, 710-718` |
| 컨테이너의 `CMD` 는 서버 하나뿐 — init 도, `init: true` 도 없으므로 **서버가 PID 1** | `Dockerfile:74`, `docker-compose.yml` |
| 재시작 시 `recover_all` → `before_start` → YouTube 가 `complete` 라고 하면 `renew` 가 **새 방송 ID** 를 만든다 (스트림과 키는 유지) | `manager.rs:383`, `youtube.rs:620-668`, `youtube.rs:576` |
| 재사용할 스트림이 없으면 `provision` 으로 떨어지고 **키까지 바뀐다** | `youtube.rs:594-597` |

### 그래서 배포가 방송을 끊는 이유

FFmpeg 은 송출 프로세스의 **자식**이고, 그 표준출력/표준오류 파이프의 **읽는
쪽이 바로 그 프로세스**다. 그러므로 `louver` 컨테이너를 재생성하면:

1. 부모가 죽고,
2. 파이프의 읽는 쪽이 사라지고,
3. 컨테이너 cgroup 의 모든 프로세스가 SIGKILL 된다.

**`nohup`·`disown`·`setsid` 로는 해결되지 않는다.** 설령 FFmpeg 을 분리해
살려둔다 해도,

- `-progress pipe:1` 의 읽는 쪽이 없어 버퍼가 차면 EPIPE/SIGPIPE 로 죽고,
- 그 전까지도 진행 정보를 **아무도 읽지 않으므로** `bytes_sent`·`uptime`·LIVE
  판정이 멈추고,
- `ProcessHandle` 이 사라져 **나중에 정상 종료시킬 방법이 없다**.

즉 "부모를 교체하면서 자식을 살린다"는 배치는 존재하지 않는다. 송출 중인
FFmpeg 을 **다른 구조로 이전하는 것은 불가능하다.** 이것은 설계 선택이 아니라
프로세스 모델의 결과다.

### 실측 (2026-10-14, 이 세션)

| 실험 | 결과 |
| --- | --- |
| 핸들러 없는 PID 1 에 SIGTERM | **무시됨** — 자체 PID 네임스페이스의 `sleep` 이 SIGTERM 을 받고도 살아남아 제 타이머로 종료 |
| `LOUVER_ROLE=all` 에서 서버 교체 | FFmpeg(5652, 부모=서버) **죽음** |
| `LOUVER_ROLE=api` + 별도 runner 에서 API 교체 | FFmpeg(5558, 부모=runner 5460) **동일 PID 생존**, `etimes` 4→19 로 증가, 재시작 로그 없음 |

첫 줄이 중요하다. 이 수정 전까지 `docker stop` 은 SIGTERM 을 **무시당하고**
유예 시간을 다 쓴 뒤 SIGKILL 로 끝났다. 즉 지금까지의 모든 배포는 FFmpeg 을
프레임 중간에 강제 종료했고 FLV trailer 도 쓰지 못했다. 이제 SIGTERM 핸들러가
있으므로 `docker stop` 은 각 FFmpeg 에게 3초의 정리 시간을 준다.

## 2. 구조 비교

| | A. 전용 worker 컨테이너 1개 | B. 방송별 컨테이너 | C. 호스트 supervisor (Docker 밖) | D. API / 실행 서비스 완전 분리 |
| --- | --- | --- | --- | --- |
| **기존 방송 중단 위험** | 전환 시 1회 | 전환 시 1회 | 전환 시 1회 + Docker 밖으로 나가는 위험 | 전환 시 1회 |
| **백엔드 독립 배포** | API 가능, worker 불가 | API 가능, **worker 도 가능** (기존 컨테이너는 옛 이미지로 계속 돈다) | API 가능, supervisor 불가 | API 가능, runner 불가 |
| **장애 복구** | 기존 `recover_all` 그대로 | 컨테이너 재시작 정책까지 더해짐 | systemd 가 봐줌 | 기존 `recover_all` 그대로 |
| **고객별 격리** | 현재와 같음 (프로세스 단위) | **최상** — cgroup/네임스페이스 분리 | 현재와 같음 | 현재와 같음 |
| **CPU·메모리** | 컨테이너 1개 추가 (~수십 MB) | 방송 수만큼 (커널 공유라 작지만 누적) | 추가 없음 | 컨테이너 1개 추가 |
| **운영 복잡도** | 낮음 | **높음** — 이미지 수명, 고아 컨테이너 회수, 로그 수집, Docker 소켓 권한 | 중간 — 배포 경로가 둘로 갈림 | 낮음 |
| **로그·상태** | 기존 stdout 그대로 | 컨테이너마다 흩어짐 | journald 로 빠짐 | 기존 stdout 그대로 |
| **기존 데이터 호환** | 완전 (같은 DB·볼륨) | 완전 | 볼륨 경로 재설계 필요 | 완전 |
| **롤백** | compose 파일 되돌리기 | 컨테이너 정리까지 필요 | 호스트 유닛 제거까지 필요 | **환경변수 하나** |
| **치명적 비용** | — | **Docker 소켓 노출** = 사실상 root | 컨테이너 모델 포기 | — |

### 선정: **D**, 같은 이미지의 두 번째 컨테이너로 구현

근거:

1. **요구사항을 정확히 만족하는 최소 변경이다.** 필요한 것은 "API 를 교체해도
   FFmpeg 이 살아 있는 것"이고, 그것은 FFmpeg 을 띄우는 프로세스가 교체 대상이
   아니면 된다. 그 이상은 지금 필요하지 않다.
2. **같은 이미지, 같은 바이너리.** 두 번째 빌드 파이프라인이 없고, 두 역할이
   DB 스키마에 대해 **버전이 어긋날 수 없다.** 역할은 `LOUVER_ROLE` 하나다.
3. **기존 아키텍처를 그대로 쓴다** (§7 "기존 아키텍처 최대한 유지").
   `supervisor.rs` 와 `manager.rs` 는 한 줄도 다시 쓰지 않았다. 바뀐 것은
   `spawn_worker`/`halt_worker`/`running_ids` 가 소켓으로 나가는지 여부뿐이다.
4. **Docker 소켓을 노출하지 않는다** — B 의 가장 큰 비용을 피한다.
5. **롤백이 환경변수 하나다.** `LOUVER_ROLE` 의 기본값은 `all` 이고, 그것은
   이 작업 이전과 완전히 동일한 동작이다.

B 를 선택하지 않은 이유는 격리가 나쁘기 때문이 아니라 — 격리는 B 가 가장
좋다 — **Docker 소켓 노출과 운영 복잡도가 지금 얻는 것보다 크기 때문**이다.
worker 코드 변경까지 무중단으로 하고 싶어지면 그때 B 가 다음 단계다. 그 판단
기준은 "runner 를 얼마나 자주 배포해야 하는가" 하나다.

## 3. 구현된 것

### 역할

`LOUVER_ROLE` = `all` (기본) · `api` · `runner`. 오타는 `all` 로 떨어진다 —
오타가 "아무 방송도 하지 않는 서버"가 되면 안 되기 때문이다.

| | HTTP | worker 소유 | lease | 스케줄러 | 복구 |
| --- | --- | --- | --- | --- | --- |
| `all` | O | O | O | O | O |
| `api` | O | X | **X** | X | X |
| `runner` | X | O | O | O | O |

`api` 가 lease 를 잡지 않는 것은 의도다. 잡으면 API 를 겹쳐 띄우는 순간
한쪽이 기동을 거부하고, 그것은 무중단 배포의 반대다.

### 제어 채널

데이터 볼륨 안의 Unix 소켓(`runner.sock`, 0600). 네트워크 서비스가 아니므로
열 포트도, 막을 방화벽도 없고 **파일시스템이 인증**이다. 명령은 네 개:

```
START <id>   → OK | ERR <사람이 읽는 문장>
HALT <id>    → OK            (동기 — 응답이 오면 FFmpeg 은 이미 멈췄다)
RUNNING      → IDS a,b,c
PING         → OK
```

- `<id>` 는 hex 만 허용한다. 저쪽에서 SQL 과 파일 경로에 들어가기 때문이다.
- `ERR` 의 문장은 그대로 올라간다. 거절된 시작이 사용자 앞에서 "실패" 로
  뭉개지면 안 된다.
- `HALT` 가 동기인 이유: 호출자는 그 다음에 YouTube 방송을 종료시킨다. 비동기면
  FFmpeg 이 이미 끝난 방송으로 계속 보내게 된다.

### 역할이 바꾸지 않는 것

`start`/`stop`/`restart` 의 **검증과 정책은 API 쪽에 그대로 남는다** — 구독
확인, 동시 송출 자리 claim, YouTube `before_start`/`after_stop`, DB 쓰기.
runner 로 가는 것은 "프로세스를 띄워라/멈춰라" 뿐이다. 그래야 거절된 시작이
사용자가 기다리는 자리에서 문장으로 돌아온다.

runner 는 그래도 **구독을 한 번 더 확인한다**. `recover_all` 이 같은 이유로 같은
확인을 반복하는 것과 같다: 이 경로는 `start` 를 거치지 않으므로, HTTP 쪽 버그가
요금제 없는 계정의 방송이 되면 안 된다.

### runner 가 없을 때

모든 명령이 소켓 경로를 포함한 문장으로 실패한다. 그리고 **그것이 안전한
동작이다**: 도달하지 못한 시작은 성공으로 보고되지 않고, 이미 송출 중인 방송은
runner 가 들고 있으므로 아무 영향이 없다. `running_ids` 만 DB 기록으로
대체한다 — runner 가 안 보일 뿐인데 대시보드가 "아무것도 안 돌고 있다"고 하면,
그것은 FFmpeg 만 보고 LIVE 라고 했던 원래 장애와 같은 종류의 거짓이다.

## 4. 전환 — 무중단이 아니다

**전환 시점에 현재 송출 중인 방송은 한 번 재시작된다.** §1 에서 본 대로 송출
중인 FFmpeg 을 이전할 방법은 없다. 이것을 무중단이라고 부르지 않는다.

그리고 재시작에는 추가 위험이 있다: `recover_all` → `before_start` 에서 YouTube
가 `complete` 라고 답한 방송은 `renew` 로 **새 방송 ID**를 받고, 따라서 **시청
URL 이 바뀐다.** 스트림과 키는 유지된다. 라이브 중인 방송은 `complete` 가
아니므로 URL 이 유지되지만, 창 안에서 확인해야 할 항목이다.

### 선택지

1. **점검 창에서 한 번에 전환.** 가장 단순하고 가장 짧다. 창을 합의해야 한다.
2. **기존 방송이 끝날 때 자연 전환.** 24/7 방송에는 "끝날 때"가 오지 않으므로
   이 서비스에는 사실상 선택지가 아니다. 예약 방송이 섞여 있다면 그 방송만
   창 없이 넘어간다.
3. **고객별 순차 전환.** 한 번에 한 방송만 재시작한다. 전체 중단은 없지만 각
   고객은 여전히 한 번 끊긴다. 창을 쪼개는 것이지 없애는 것이 아니다.

어느 쪽이든 **고객은 한 번 끊긴다.** 이것을 숨기지 말고 사전에 알려야 한다.

## 5. 단계별 계획

### PHASE A — 진단 (운영 변경 없음)

- **진입 조건:** 없음. 지금 바로 가능하다.
- **할 일:** `scripts/youtube-audit.sh --host … --binary …` — 읽기 전용.
  컨테이너를 만들지도, 멈추지도, 재시작하지도 않는다. FFmpeg 에 시그널을 보내지
  않는다. DB 는 SQLite 가 강제하는 읽기 전용으로 연다.
- **중단 조건:** 바이너리의 glibc 가 호스트보다 새로우면 스크립트가 먼저
  거부한다. `cloud.db` 가 현재 바이너리보다 오래된 스키마면 반쯤 읽지 않고
  멈춘다.
- **롤백:** 해당 없음 — 바꾼 것이 없다. 복사한 바이너리는 스크립트가 지운다.

### PHASE B — PR #12 적용 준비 (운영 변경 없음)

- **진입 조건:** PHASE A 가 끝나고, `STUCK TESTING`/`STUCK READY` 로 나온 방송을
  YouTube Studio 에서 '실시간 시작' 으로 복구했을 때.
- **할 일:** 적용 전 확인 — 추가되는 nullable 컬럼
  (`broadcasts.youtube_status_at`) 이 `ensure_column` 으로 기동 시 붙는다는 것,
  `stop_grace_period` 가 다음 배포에 반영된다는 것, 롤백 시 구 바이너리가 그
  컬럼을 select 하지 않으므로 그대로 읽힌다는 것.
- **중단 조건:** 고객과 점검 창을 합의하지 못하면 중단. 백엔드 변경은 창 없이
  적용할 방법이 없다.
- **롤백:** 이전 이미지 재배포. 마이그레이션은 추가(additive)뿐이다.

### PHASE C — API/runner 분리 (운영 적용은 별도 승인)

- **진입 조건:** PHASE B 가 끝나고, 아래 테스트가 테스트 환경에서 재현되고,
  점검 창이 잡혔을 때.
- **할 일:** `COMPOSE_FILE` 에 `docker-compose.split.yml` 을 추가하고
  `louver-runner` 를 먼저 올린 뒤 `louver` 를 `api` 역할로 재생성.
- **중단 조건:** runner 가 lease 를 잡지 못하면 (다른 프로세스가 데이터
  디렉터리를 쓰고 있으면) 즉시 중단하고 원인을 조사한다. 억지로 띄우면 방송
  하나에 FFmpeg 두 개가 붙는다.
- **롤백:** `COMPOSE_FILE` 에서 이 파일을 빼고 `louver` 를 재생성한다.
  `LOUVER_ROLE` 이 없으면 `all` 이고, 그것은 이 작업 이전과 동일하다.
  **롤백도 방송을 한 번 끊는다** — 롤백 역시 부모 교체이기 때문이다.
