# 247streams 저장소 구조와 정리 절차

영상 하나가 디스크에서 무엇을 차지하는지, 그게 언제 늘어나고 언제 줄어드는지,
그리고 남은 파일을 **안전하게** 확인하는 방법.

배포는 [CLOUD_TESTING.md](CLOUD_TESTING.md), 장애 대응은
[OPERATIONS.md](OPERATIONS.md) 를 보세요.

---

## 1. 영상 하나가 차지하는 것

업로드된 파일은 두 가지 중 하나가 됩니다.

| 판정 | 디스크 | `prepared_path` |
| --- | --- | --- |
| **변환이 필요 없음** (`mode=direct`, MP4 계열) | **원본 1벌** | 원본과 같은 경로 |
| 변환이 필요함 (`hybrid` / `live_normalize` / `canonical`) | 원본 + 변환본 2벌 | 새 파일 |

변환이 필요 없다는 것은 코덱·픽셀 포맷·해상도·프레임레이트·H.264 프로파일/레벨·
오디오·**키프레임 간격까지 전부 그대로 송출 가능**하다는 뜻입니다. 이때는 변환본을
만들지 않고 원본을 그대로 방송 입력으로 씁니다.

Playlist Maker Pro 의 247streams optimized export 가 바로 이 조건을 만족하도록
만들어져 있습니다. 그런 파일을 올리면 683MB 를 올려 683MB 만 씁니다.

### 왜 예전에는 2벌이었나

준비 단계는 항상 파일을 하나 만들어 냈습니다. `direct` 여도 마찬가지였고, 그건
컨테이너를 우리 타임스케일로 다시 쓰기 위해서였습니다. 하지만 concat 이 요구하는
"항목끼리 모양이 같을 것"은 `prepared_signature` 비교가 이미 강제하고 있고, 그
서명은 **실제로 방송이 읽을 파일을 probe 해서** 기록합니다. 그래서 우리 컨테이너
계열인 파일에 대해서는, 다시 쓰기가 같은 바이트의 두 번째 사본을 만드는 것 외에
하는 일이 없었습니다.

## 2. 화면에 나오는 숫자

영상 목록의 크기 표시는 이렇게 읽습니다.

```
683 MB · 변환 없이 그대로 송출          ← 1벌
11.0 GB (원본 683 MB + 변환본 10.4 GB)  ← 2벌
11.0 GB                                 ← 이 릴리스 이전에 준비된 영상
```

세 번째는 `source_bytes` / `prepared_bytes` 가 `NULL` 인 예전 행입니다. 합계는
정확하지만 내역을 모르므로, 지어내지 않고 합계만 보여줍니다.

**저장 한도(quota)는 언제나 합계입니다.** `media.size_bytes` 의 SUM 이고, 이
릴리스에서 그 의미는 바뀌지 않았습니다.

## 3. 변환본이 교체될 때

플레이리스트에 형식이 섞이면 항목들이 표준 형식으로 다시 준비됩니다. 그때 순서는
**반드시** 이렇습니다.

1. 새 변환본을 만든다
2. ffprobe 로 서명을 읽는다
3. 이전 변환본을 `storage_trash` 에 기록한다 — **지우지 않는다**
4. `prepared_path` 를 새 파일로 바꾼다

어느 단계에서 죽어도 행은 *존재하는* 파일을 가리킵니다.

3번에서 지우지 않는 이유는 하나입니다. 재준비를 시작시킨 그 플레이리스트의 방송이
지금 송출 중일 수 있고, 그 FFmpeg 는 옛 파일을 열어 둔 채입니다. Linux 에서
unlink 해도 그 방송은 계속 돌지만, **서버가 재시작하는 순간 복구가 없는 경로를
열고 죽습니다.** 남겨 두면 디스크를 쓰고, 지우면 방송을 잃습니다.

> production 에서 발견된 2.0GB 짜리 orphan 이 정확히 이 경우입니다. 다만 당시엔
> 기록도 남지 않아서 아무도 그 파일이 왜 있는지 알 수 없었습니다.

## 4. 남은 파일 확인 — `--audit-media-storage`

```bash
docker compose exec louver louver-server --audit-media-storage
docker compose exec louver louver-server --audit-media-storage --json
```

**이 명령은 아무것도 지우지 않습니다. 지우는 옵션도 없습니다.**

파일마다 이렇게 판정합니다.

| 역할 | 뜻 |
| --- | --- |
| `source (직접 송출)` | 업로드이며, 방송이 읽는 파일이기도 함 |
| `source` | 업로드. 옆에 변환본이 있음 |
| `prepared` | 변환본. 방송이 읽는 파일 |
| `retired` | 재준비로 교체된 옛 변환본 (`storage_trash` 에 기록됨) |
| `orphan` | 어떤 행도 가리키지 않는 파일 |

**`[정리 가능]` 은 아래가 전부 참일 때만 붙습니다.**

- 어떤 `media` 행도 이 파일을 (원본으로도 변환본으로도) 가리키지 않음
- `work/*/manifest.txt` 중 어느 것도 이 파일을 적고 있지 않음
- 어떤 프로세스도 이 파일을 열고 있지 않음
- **그리고 "열린 파일"을 실제로 확인할 수 있었음**

마지막 조건이 빠지면 전부 "정리 불가"로 답합니다. 모르면 지우지 않습니다.

manifest 를 보는 이유는 DB 만으로는 알 수 없는 참조이기 때문입니다. FFmpeg 는
시작할 때 받은 manifest 를 **매 바퀴 다시 읽습니다.**

### 실제로 지울 때

1. 방송이 도는 동안에는 지우지 마세요. `--audit-media-storage` 를 방송이 끝난 뒤
   다시 돌려 같은 파일이 여전히 `[정리 가능]` 인지 확인합니다.
2. 목록에 나온 경로를 눈으로 확인합니다.
3. 지우기 전에 데이터베이스를 백업합니다 ([OPERATIONS.md](OPERATIONS.md) 2번).
4. 사람이 `rm` 합니다. 한 번에 하나씩.

자동 삭제는 만들지 않았습니다. 이 디렉터리에 있는 건 수강생이 몇 시간에 걸쳐 만든
영상이고, 잘못 지웠을 때 되돌릴 방법이 없습니다.

## 5. 예전에 만들어진 큰 변환본 (migration)

이 릴리스는 **이미 있는 파일을 건드리지 않습니다.** 부팅해도, 배포해도, 아무 행도
재준비되지 않고 아무 파일도 지워지지 않습니다. 새 규칙은 *다음* 업로드와 *다음*
재준비부터 적용됩니다.

예전 방식으로 만들어진 큰 변환본(예: 716MB 원본 → 11.1GB canonical)을 줄이려면,
방송을 끊지 않는 순서로 해야 합니다.

**절대 먼저 하면 안 되는 것:** 옛 변환본 삭제. 언제나 새로 만든 뒤에 교체합니다.

### 한 영상씩, 방송이 멈춰 있을 때

1. 그 영상을 쓰는 방송이 **중지 상태인지** 확인합니다.
   ```bash
   docker compose exec louver louver-server --diagnose
   ```
2. 재준비를 걸어 새 판정을 받습니다. 사용자가 영상 목록에서 그 영상을 지우고
   다시 올리는 것이 가장 단순하고 안전한 방법이며, 코드 경로도 이미 검증된
   업로드 경로 그대로입니다.
   - `mode=direct` 로 판정되면 → 변환본이 생기지 않고 원본 1벌만 남습니다.
   - 변환이 필요하면 → 필요한 최소 변환만 걸립니다(전체 1080p30 재인코딩이
     아니라 `live_normalize`).
3. 옛 파일은 `--audit-media-storage` 에 `orphan` 으로 나타납니다. 4번 절차대로
   확인하고 지웁니다.

### 방송 중인 영상

**그대로 둡니다.** 방송이 끝난 뒤에 위 절차를 밟습니다. 송출 중인 파일을
교체하거나 지우는 절차는 이 문서에 없습니다. 그런 절차는 필요하지 않습니다 —
기다리면 됩니다.

### 예상 효과

production 에서 확인된 실제 수치 기준입니다.

| | 지금 | 재준비 뒤 |
| --- | --- | --- |
| `playlist-export.mp4` | 716MB + 11.1GB = **11.85GB** | direct 면 **716MB** |
| `Cozy.mp4` | 653MB + 9.0GB (+ orphan 2.0GB) = **11.6GB** | direct 면 **653MB** |

## 6. 이 릴리스가 바꾸지 않은 것

- 저장 한도 값 (Basic 5GB / Pro 10GB / Business 20GB)
- `media.size_bytes` 의 의미(합계)와 그것을 쓰는 모든 quota 계산
- 변환이 **필요한** 파일의 처리 — `hybrid` / `live_normalize` / `canonical`
  정책은 그대로입니다
- 플레이리스트 호환성 판정 — 여전히 서명 비교이고, 섞이면 표준 형식으로 수렴
- 기존 DB 행. 새 컬럼은 추가만 되고 기본값은 `NULL` 입니다
